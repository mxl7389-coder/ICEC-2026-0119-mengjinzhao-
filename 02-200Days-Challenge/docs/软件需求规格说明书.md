## 1. 项目概述

### 1.1 项目背景

校园日常学习与管理中的高频痛点：

1. 校园通知分散在不同渠道，重要信息容易遗漏。
2. 通知内容较长，手动整理截止时间、地点和任务效率较低。
3. 实验室器材借用、归还、库存盘点依赖人工登记。
4. 器材数量不准确，容易出现逾期、损坏和账实不符。
5. 错题整理与知识点归纳耗费大量时间。
6. 校园信息缺少统一查询入口。

### 1.2 项目目标

- 实现校园通知自动导入和智能信息提取。
- 实现通知任务自动生成和提醒。
- 实现实验室器材档案、借还、盘点和异常管理。
- 实现 AI 错题识别、分析和复习管理。
- 实现基于本地资料的 AI 校园问答。
- 建立完整的运行监控、异常处理和数据备份机制。
- 完成至少连续 7 天的真实运行验证。
- 保留至少 3 次可追溯的 GitHub 迭代记录。
- 收集至少 8 位真实用户的使用反馈。

### 1.3 设计原则

1. 本地优先：业务数据和 AI 推理尽可能在本地完成。
2. 模块化：业务模块独立，方便后续扩展。
3. 可追溯：重要操作均保留审计记录。
4. 人工确认：AI 生成的信息不得未经确认直接执行重要业务操作。
5. 数据安全：支持备份、恢复和访问权限控制。
6. 稳定运行：具备异常捕获、超时处理和恢复机制。

> **当前实现状态（v6.2.0）**：原则 1、2、5、6 已落地（零依赖本地运行、模块拆分、scrypt 密码哈希 + 角色权限 + SHA256 备份校验、全局异常兜底）；原则 3 由 `data/audit.json` 业务审计表落地；原则 4 由「通知人工审核后才入库」与「版本差异先预览再确认」落地。AI 推理部分采用**确定性本地规则引擎**，不做生成式推理，因此不存在"AI 擅自执行"的风险。

## 4. 非功能需求

### 4.1 性能

- 普通本地查询目标 ≤ 500ms；普通界面操作目标 ≤ 1s。
- AI 调用耗时独立统计，不以固定推理时间作为所有设备的强制标准。
- 文件处理采用异步任务，避免阻塞界面。

> **实测**：原始日志 882 条，耗时 p50 **1.64ms**、p95 **79.93ms**、最大 **186ms**，均低于 500ms 目标；文件解析在浏览器 `FileReader` 中异步完成，不阻塞服务端事件循环。

### 4.2 稳定性

- 程序意外关闭后业务数据不丢失：`lib/store.js` 采用 `writeFileSync(tmp)` + `renameSync` **原子写入**，并带文件指纹缓存失效，避免多实例覆盖。
- 数据库异常时记录错误；AI 服务不可用时不影响基础业务；网络断开时本地功能仍可用。
- 运行日志按自然日采集并每日同步，逐日原始记录见 [`process_logs/`](../process_logs/)。

### 4.3 安全性

- 本地数据默认不上传云端；用户密码不得明文存储（scrypt 加盐哈希）。
- 重要操作保留审计记录；不允许未经授权修改器材库存。
- 敏感信息不得写入普通运行日志（日志只含脱敏时间戳、模块、动作、耗时、状态、错误码）。
- 数据备份具备完整性检查：SHA256 checksum，可校验、拒绝被篡改的备份、显式确认后恢复。

> 另已加固：CSP `script-src 'self'`、`Referrer-Policy: same-origin`、`X-Content-Type-Options: nosniff`、写请求 `Origin/Referer` 同源校验、畸形 URL/Cookie 不会导致进程退出、5xx 不回传内部路径。

### 4.4 可维护性

前后端分离、业务模块独立、AI 服务统一封装、数据访问统一管理、使用 Git 版本控制、提供 README 与开发文档。

> **已实现**：`server.js`（传输层）/ `lib/api.js`（业务路由）/ `lib/store.js`（统一数据访问）/ `lib/assistant.js`（助手适配层）/ `lib/extractor.js`（提取引擎）分层清晰；README 与 `docs/` 提供运行、架构、数据和测试说明。

## 5. 数据库设计（SRS 规划）

第一版规划采用 SQLite，核心 24 张表：

`users`、`roles`、`user_roles`、`notices`、`notice_attachments`、`notice_extractions`、`notice_versions`、`tasks`、`reminders`、`equipment`、`equipment_categories`、`equipment_transactions`、`inventory_sessions`、`inventory_items`、`equipment_incidents`、`wrong_questions`、`knowledge_points`、`study_records`、`chat_sessions`、`chat_messages`、`audit_logs`、`telemetry_events`、`backups`、`app_settings`。

要求：外键约束、合理索引、事务处理、迁移版本管理。

> **当前实现状态**：采用零依赖 JSON 原子存储（`data/*.json`，8 个数据集），**未使用 SQLite**。逐表映射与迁移方案见 [`数据库设计说明.md`](数据库设计说明.md)。不迁移的原因：引入 SQLite 依赖会破坏「零依赖即跑」与本地优先约束，属后续阶段工作。

## 6. 核心业务流程

1. **通知**：导入 → 文件解析 → 提取 → 字段校验 → **人工审核** → 入库 → 生成待办 → 设置提醒 → 完成任务。
2. **器材借还**：查询 → 提交申请 → 管理员审核 → 确认借出 → 更新库存 → 归还登记 → 检查状态 → 完成。
3. **盘点**：创建任务 → 录入实际数量 → 对比账面 → 生成差异 → 人工核查 → 确认调整 → 审计日志。
4. **AI 调用**：用户操作 → 后端校验 → 调用本地能力 → 获取结果 → 结构化校验 → 人工确认（必要时）→ 保存 → 记录 Telemetry。

> 流程 1 完整实现；流程 2 实现「归还登记 + 库存重算」；流程 4 以确定性规则引擎实现，不含模型调用。

## 7. 技术架构

| 层 | SRS 规划 | 当前实现 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite + Tailwind + Electron | 原生 HTML/CSS/JS，三套独立入口（封面 / 用户端 / 管理端），无构建步骤 |
| 后端 | Python + FastAPI + SQLAlchemy + Alembic + Pydantic | Node.js 原生 `http` + 自研路由，零第三方依赖 |
| 数据 | SQLite + 本地文件 | JSON 原子文件 + JSONL telemetry |
| AI | Ollama + 本地 LLM + OCR + RAG | 本地规则引擎（`extract_engine: 'local-rules'`）+ 离线检索助手 |
| 工程 | Git / GitHub / pytest / Playwright / 结构化日志 | Git + 自研 `scripts/smoke-test.js`（132 项）+ JSONL 结构化日志 |

> 详见 [`系统架构设计.md`](系统架构设计.md)。二者属于**不同阶段**：当前交付是第一阶段可运行版本，保留前后端分离、模块化、统一数据访问、自动 Telemetry 与 Git 迭代约束。
