# 8 位真实用户反馈 · 收集指引

> 对应项目四验收项「至少 8 位真实用户，有实际使用记录、有反馈问卷或访谈、记录发现的问题、根据反馈进行改进」。
> **当前状态：0 份**。`data/feedback.json` 为 `[]`，[`docs/用户反馈表.md`](用户反馈表.md) 是 8 份空白问卷，网页反馈表单字段已与之对齐，管理端「反馈收集」页显示「已收 N/8」。
> 系统**不代填、不生成示例反馈**——编造反馈会直接违背题目「防摆拍」要求。本文只提供最省力的真实收集方式。

---

## 1. 为什么要真实收集

题目把「8 位真实用户反馈」与「连续 7 天真实运行日志」「3 次基于日志的 Git 迭代」并列，核心是验证程序**真的被人用过、真的按反馈改过**。因此评价时会看：

- 反馈是否分散在不同日期、不同身份；
- 是否记录了具体「卡住的地方」而不是笼统好评；
- 是否有一条「根据反馈改进 → 新的 Git 提交」的链。

雷同的 8 份好评、同一时间戳、无具体问题描述，反而会被判定为摆拍。

---

## 2. 最快的操作路径（约 10 分钟准备）

### 步骤 1：让同学能打开网站

在 `E:\校园软件` 启动局域网模式：

```bash
node server.js --lan --port 5174
```

终端会打印 `http://10.1.44.109:5174/` 这类**物理网卡**地址（VirtualBox / VMware / WSL 的 `192.168.x` / `172.x` 不要发）。同学手机连同一 Wi-Fi 即可打开。

> 首次需要管理员放行防火墙（一次即可，需管理员身份的 PowerShell）：
> ```powershell
> New-NetFirewallRule -DisplayName 'CampusDesk LAN 5174' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5174 -Profile Any -RemoteAddress LocalSubnet
> ```

### 步骤 2：给每位同学一个试用身份

管理端 → 「账号管理」创建学生账号（**不要给管理员账号**）。每人用自己的账号登录，数据按 `owner_id` 隔离，互不干扰。

### 步骤 3：给一个具体任务，别只说「随便看看」

建议直接发这段话（可直接复制）：

> 帮我试一下校园事务台，3 分钟就够：
> 1. 打开 `http://<你的IP>:5174/user/`，用我给你的账号登录。
> 2. 在「通知与任务」粘贴一条**真实的**班群/教务通知，点结构化提取，看看时间、地点、截止日期抽得对不对，再人工确认保存。
> 3. 在「器材借还」看一眼器材清单，或登记一次借用。
> 4. 最后在「使用反馈」填写问卷，重点写**哪里卡住了 / 哪里看不懂**。
> 谢谢！你的吐槽对我最有用。

### 步骤 4：两种填写方式二选一

| 方式 | 操作 | 结果落在 |
| --- | --- | --- |
| **网页表单（推荐）** | 用户端「使用反馈」页填写并提交 | `data/feedback.json`，管理端「反馈收集」页实时显示 `已收 N/8` |
| **线下问卷** | 打印 / 发送 [`docs/用户反馈表.md`](用户反馈表.md) 中的 8 份表格 | 手写或电子填写后，把内容整理进 `docs/用户反馈表.md` |

网页表单字段与线下问卷一致：`role`（身份）、`module`（试用模块）、`score`（1–5 分）、`task_done`（实际完成的任务）、`problem`（遇到的问题）、`liked`（最有帮助的地方）、`reuse`（是否愿意再次使用）。

## 3. 收集时的注意事项

- **不要用自己的账号替同学提交 8 次**，日志里会显示同一 session / 同一时间段，容易被识别。
- 让同学填**真实身份**（年级/角色即可，可不填姓名），8 份尽量覆盖不同身份（如 5 位同学、2 位班干部、1 位实验室助理）。
- 至少留下 **2～3 条具体的负面或改进意见**，这是「根据反馈改进」的依据。
- 反馈原文属于敏感内容：`.gitignore` 已排除 `data/`，网页反馈正文不会写进运行日志，**不会上传到 GitHub**。仓库里公开的是问卷模板、字段定义与收集进度，不是个人隐私。

---

## 4. 收齐之后要做的两件事

1. **按反馈做一次真实改进**，形成新的 Git 提交。例如：
   - 若多人反馈「不知道怎么导入」→ 改进导入区提示文案 → 提交 `fix: 依据 8 位反馈优化导入引导`；
   - 若多人反馈「截止日期看不清」→ 调整看板日期显示 → 提交并在 README 记录依据。
   这一步让「反馈 → 迭代」形成闭环，是评分点里明确要求的。
2. **更新状态文档**：在 [`docs/仓库交付自查.md`](仓库交付自查.md) 与 [`docs/7天运行报告.md`](7天运行报告.md) 中把「0 份」改为实际份数，并附上改进提交的 hash。

---

## 5. 与连续 7 天日志一起做（省时间）

收集反馈的每一天，本身就会产生真实 HTTP 请求日志。所以：

```bash
# 当天收工前执行，生成日报并自动 git commit
node scripts/daily-report.js --sync
```

同一批真实试用既能攒够 8 份反馈，也能把连续运行天数从当前 1 天推到 7 天（预计达标日 **2026-11-28**）。一举两得，不需要额外"补日志"。
